# Echo — production readiness mega report

**Purpose:** A single, opinionated view of **how close Echo is to “100%”** for two different finish lines: a **shippable text-first product** versus a **full-feature platform** (voice, import, deep scale, full feature parity). Numbers are **engineering estimates** from in-repo docs + CI + code paths — not financial or marketing metrics.

**As of:** 2026-06-01 — documentation and CI narrative reconciled with repo (Tauri mobile, Cypress E2E smoke in CI, History API navigation). Product/engineering scores unchanged from April refreshes unless noted below. **Authoritative detail** still lives in linked specs and in code; this file **synthesizes** them.

**Deployment scale stance:** Echo **max-optimizes for a single Node realtime tier** (one primary API process, in-memory Socket.IO). **Multi-node / distributed** Socket.IO (`NATS_URL`), cross-replica presence, and shared rate limiting are **not** the default investment until on the order of **~50,000 average concurrent users** (CCU). See [STACK.md](../overview/STACK.md) (Scale strategy) and [realtime-scaling.md](../infra/realtime-scaling.md). Pillar **7 — Scale-out & multi-node** stays lower priority **by design** until that threshold.

## 1. How to read “100%”

| Finish line                           | What “100%” means (working definition)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Horizon A — Serious text chat MVP** | Auth’d users can run **real servers, channels, RBAC, moderation, 1:1 DMs, blocks/reports, custom server emoji**, on **Postgres**, with **contract-tested** REST + Socket.IO, **metrics**, and **no mock API in production**. One primary API process is OK; uploads optional via `ECHO_S3_*`.                                                                                                                                                                                                                                                                    |
| **Horizon B — large-scale product**   | Everything in A, plus **first-class server/voice/SFU**, **mature multi-node** realtime (shared limits, presence semantics, ops), **durable rich media & polls**, **group DMs** on the Echo graph, **personal emoji packs**, **import pipeline to completion**, **E2E test grid**, **advanced auth** (per [AUTHENTICATION_PLAN.md](../plans/AUTHENTICATION_PLAN.md)), and **RBAC audit UX** that matches enterprise expectations. **Forum/channel thread surfaces are not a planned product scope; when this doc says “threads,” it means DM thread lists only.** |

Most of Echo’s **backend contract and RBAC depth** score well on **Horizon A** but **Horizon B** is still dominated by **voice, scale-out polish, and product breadth**.

### 3.2 RBAC

Source: `[RBAC_COMPLETENESS_REPORT.md](../infra/rbac/RBAC_COMPLETENESS_REPORT.md)`, `[permission-compat.md](../infra/rbac/permission-compat.md)`.

- **Engine:** treat as **100% complete** relative to the documented plans (primitives guard, merge semantics, overwrites, traces, performance work, cache invalidation).
- **Remaining:** richer **audit/diff UX**, optional purer trace representation, and **integration test** ambition (full `evaluatePermissionSet` against Postgres in one suite — called out in RBAC doc).

### 3.3 Realtime, scale, presence

Sources: `[realtime-scaling.md](../infra/realtime-scaling.md)`, `[STACK.md](../overview/STACK.md)`.

- **Single process:** strong — rooms gated on DB membership, persisted path only.
- **Multi-process:** **adapter exists** when `NATS_URL` is set; **not** the same as finished **cross-node presence**, **shared rate limiting**, or **validated staging runbooks** for every workspace event.
- **JetStream / platform NATS:** explicitly **deferred** beyond Socket.IO fan-out.

### 3.4 Safety, DMs, social

- **Blocks + reports + REST:** `/api/v1/echo/blocks`, `/reports/user`; profile ⋯ (copy user ID, report, block) on expanded profile, DM profile panel, member popout.
- **1:1 DMs:** **Echo graph** — `POST /dm/open`, `GET /dm/threads`, block enforcement.
- **DM discoverability (client):** **Server rail** shows up to **three** unread **1:1** threads (last message from peer, not active channel, unread vs `lastReadMessageIdByChannel`); clicking opens that DM; **fourth** control **`+N`** opens the DM panel on the messages list **without auto-opening the latest thread** (`openDmInboxFromRailOverflow` / `dispatchNav` in layout controller).
- **Group DM / thread parity:** **Group DMs** persist on the Echo graph (`POST /dm/group/open`, member table); **local `dm-group-*`** remains mock/offline fallback when server create fails or in demo mode (see [DMs pillar](../plans/messaging/DMS_PILLAR_TO_100.md)).
- **Pillar roadmap:** [DMs pillar](../plans/messaging/DMS_PILLAR_TO_100.md) — shipped scope + **deep polish** notes (not pillar % blockers).

### 3.5 Custom emoji & uploads

- **Server emoji:** end-to-end real (settings → picker → render + usage counters); image bytes via presign when configured.
- **Uploads:** **env-gated**; production without S3 config means **503** on presign, not silent degrade. Chat, avatars/banners, server icons, and emoji share the same presign route with distinct **authorization** and **key prefixes**; configure **bucket CORS** for browser `PUT`.
- **Operator Checklist (S3/CORS):**
  - **`ECHO_S3_BUCKET`**, **`ECHO_S3_REGION`**, **`ECHO_S3_ACCESS_KEY`**, **`ECHO_S3_SECRET_KEY`** (required for 200).
  - **Bucket CORS:** Browser `PUT` requires a CORS policy on the bucket allowing the frontend origin with `PUT` method and `Content-Type` header.
  - **Public Access:** Uploaded objects must be publicly readable if using the returned public URLs directly.
- **CI:** `npm run test:echo:uploads -w backend` runs in the default **`echo-backend-ci.yml`** job (Postgres env).

### 3.6 Voice, import, full-feature finish line

- **Voice:** [STACK.md](../overview/STACK.md) documents **LiveKit** as the SFU; **code** includes **Layer 1** session + webhooks + Vue client (AV, speaking, stats, mute/deafen, reconnect, tab teardown) and **server** **`RoomServiceClient`** kick — see [livekit-vc-layer-1-progress.md](../plans/livekit-vc-layer-1-progress.md) and [livekit-production.md](../operations/livekit-production.md) (operator checklist; repo ships metrics **`hooks_livekit`**, alerts, dashboards). **Horizon B** still needs **live** hosted SFU/TURN (operator) and product depth vs full-feature expectations.
- **Import:** **Automated** import from bot export covers **metadata, roles, channels, role/@everyone overwrites** (allow/deny→partial at import time) and optional **per-channel** message pull; **`members.jsonl`**, **member overwrites**, **forum/stage/thread** types, and **full** message history remain **weak**—[discord-import-readiness.md](../operations/discord-import-readiness.md) §6.

### 3.7 Frontend, quality, developer experience

- **Production build:** forces real Echo APIs.
- **Mock Mode:** confined to local development (`VITE_USE_MOCK_DATA`). Shipped artifacts have no mock runtime path; `useMockData` throws if accessed in mock mode in production.
- **Theme / lint:** **complete** for the “no raw colors outside token layer” bar ([theme-system-progress.md](../plans/theme-system-progress.md), [theme-enforcement-hardening-plan.md](../plans/theme-enforcement-hardening-plan.md)): **`npm run lint:style -w web`** (SCSS + Vue SFC styles) and **`npm run lint:theme -w web`** in CI; Amoled/Sunny remain **preference aliases** mapping to `dark`/`light` on the DOM only.
- **Tests:** Vitest breadth growing — see [test-coverage-plan.md](../plans/test-coverage-plan.md); **Cypress E2E smoke** in CI; broader component and product E2E grids still thin vs a mature product.
- **DM rail UX:** Unread **1:1** entry points on the left rail (`ServerList` + `dmIncomingRailCluster` in `useAppLayoutController`) — no separate contract; relies on existing message + read-state data.

### 3.8 Observability & ops

- **Metrics:** `**GET /api/v1/metrics`** exposes `prom-client` defaults plus Echo counters/histograms (socket branches, `message_failed`, persist results, search latency, snowflake generator, workspace events, permission denials, **REST RED** `echo_rest_http_*`, `**echo_dm_open_total`**) — see `[ECHO_CONTRACT_V1.md](../contracts/ECHO_CONTRACT_V1.md)`§Metrics and`[server/backend/src/observability/echoMetrics.ts](../../server/backend/src/observability/echoMetrics.ts)`.
- **Logs:** Structured fields with stable `**msg`** strings on hot paths; requests use Fastify `**X-Request-Id`**/`req.id`with a pino child binding`\*\*correlationId\*\*` (`registerEchoHttpObservability`); sockets may pass the same header on the handshake as a fallback when the message payload omits `correlationId`.
- **Runbooks in-repo:** `[snowflake-cutover.md](../operations/runbooks/snowflake-cutover.md)`, `[postgres-incident.md](../operations/runbooks/postgres-incident.md)`, `[nats-socketio.md](../operations/runbooks/nats-socketio.md)`, `[jwt-socket-auth.md](../operations/runbooks/jwt-socket-auth.md)`, `[multi-replica-socketio.md](../operations/runbooks/multi-replica-socketio.md)` — see §9 documentation map.
- **Alerting / dashboards as code:** `[server/ops/monitoring/prometheus/rules/](../../server/ops/monitoring/prometheus/rules/)` and optional `[server/ops/monitoring/grafana/echo-overview.json](../../server/ops/monitoring/grafana/echo-overview.json)`.
- **Gaps vs a stricter “100%”:** **OpenTelemetry** export is **opt-in** via `**OTEL_EXPORTER_OTLP_ENDPOINT`** (`[otel.ts](../../server/backend/src/observability/otel.ts)`, [Observability pillar doc](../operations/ops/OBSERVABILITY_OPS_TO_100.md) §7); without it, no trace pipeline. ## 5. Risks that pull the % down

1. **Horizon B dependency on voice** — **dev SFU path** and **in-repo** prod hardening (docs, alerts, dashboards) exist; **live** TURN/hosted LiveKit and **competitor-depth** voice UX still drive expectation gaps until operators wire infra.
2. **Multi-node without ops discipline** — adapter alone does not fix **presence**, **limits**, or **staging validation**.
3. **Polls and attachment abuse** — multi-attach is durable when S3 + https URLs are used; **polls** and **rate limits on presign** vs competitor depth remain gaps.
4. **Import** — legal/ops complexity even after code is “ready.”
5. **Auth** — Option A **cookie + Redis** spine and **passkeys** are implemented; see pillar 2 row and `[OPTION_A_SESSION_ARCHITECTURE.md](../infra/auth/OPTION_A_SESSION_ARCHITECTURE.md)`. Further items in `[AUTHENTICATION_PLAN.md](../plans/AUTHENTICATION_PLAN.md)` are incremental hardening, not a parallel stack.
6. **Test pyramid** — strong **contract/integration** on backend; **E2E** not in CI.

## 10. Bottom line

Echo is **past the “demo with sockets” phase**: for **Horizon A**, the **core server contract, RBAC engine, moderation hooks, safety, 1:1 DMs (including left-rail unread shortcuts), server emoji, truthful in-server message search, and closed theme/token enforcement** form a **credible** base for a **text-first** product **on one primary realtime tier**, with an **optional** multi-process path via `**NATS_URL`**. **Horizon B** remains far: **voice at production/competitor depth** (vs **Layer 1 LiveKit** now in-repo for **dev**), **mature scale-out**, **import completion** (members, member overwrites, full history vs today’s structure + optional messages), **personal emoji**, and **advanced auth** are the main reasons a **full-feature “100%”** score stays in the **~52–62%** band (aligned with §2.1) while a **focused chat MVP** sits in the **~90–95%\*\* band (aligned with §2.1). Forum/channel thread surfaces are intentionally not part of the product scope.
