# Client Charter Leak Goals

This checklist tracks the main places where frontend code must not become the authority for domain truth. It is intentionally row-numbered because several architecture notes cite specific rows while documenting cleanup work.

Authoritative rule: [agents.md](../overview/agents.md). Companion inventories: [client-charter-violations.md](./client-charter-violations.md) and [client-layer-violations.md](./client-layer-violations.md).

| Row | Goal                                                                       | Done when                                                                                                                        |
| --- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Layout composition remains orchestration, not domain authority.            | `useAppLayoutController` wires state and intents without deciding canonical server, channel, role, permission, or message truth. |
| 2   | Layout reactive graph does not merge canonical workspace state.            | Reactive layout helpers can derive display state but do not reconcile competing workspace snapshots.                             |
| 3   | Server/channel identity comes from the Echo domain model.                  | UI helpers consume normalized domain outputs instead of inventing fallback ids or ownership rules.                               |
| 4   | Message history ordering is owned by message domain services.              | View code renders ordered collections provided by the message authority.                                                         |
| 5   | Read state clearing rules live below the view layer.                       | Components do not decide whether a read cursor supersedes last-message state.                                                    |
| 6   | DM thread identity and activity merge below the shell.                     | Layout and panel code consume thread view models rather than merging API and realtime payloads directly.                         |
| 7   | Presence semantics are centralized.                                        | Client views do not reconcile presence from multiple sources or invent staleness rules.                                          |
| 8   | Role ordering and hierarchy are owned by permissions/roles services.       | UI receives precomputed order, top-role, and expanded capability data.                                                           |
| 9   | Permission gating defaults are explicit and server-backed.                 | Any optimistic or permissive client behavior is labeled as UX only and server enforcement remains mandatory.                     |
| 10  | Moderation state is canonical in server/backend/domain responses.          | Client code does not infer ban, timeout, or block authority from partial UI state.                                               |
| 11  | URL parsing stays navigation glue.                                         | Route helpers map URLs to intents without selecting domain fallbacks as truth.                                                   |
| 12  | URL navigation fallback authority is not in the shell.                     | Invalid paths resolve through a domain or router policy helper, not ad hoc layout priority rules.                                |
| 13  | Chat list grouping is presentation only.                                   | Client grouping does not alter canonical channel, thread, or unread state.                                                       |
| 14  | Chat list ordering rules are domain-owned when they affect shared meaning. | Activity, unread, and mention ordering are produced by the relevant domain service.                                              |
| 15  | Echo HTTP boundary is normalized at one edge.                              | API modules normalize request/response shapes before state reaches stores or views.                                              |
| 16  | Major payload contracts are checked against the documented Echo API.       | Contract checks cover REST and Socket.IO payloads that define shared meaning.                                                    |
| 17  | Socket payload reconciliation is centralized.                              | Realtime handlers route payloads to domain services instead of mutating view stores independently.                               |
| 18  | Optimistic updates have a single rollback authority.                       | Components emit intents and do not each invent rollback semantics.                                                               |
| 19  | Cache freshness is not decided by components.                              | Freshness and invalidation rules live in data/domain services.                                                                   |
| 20  | Offline/mock behavior is visibly separate from real Echo behavior.         | Mock fallbacks cannot silently become production truth.                                                                          |
| 21  | Import preview state stays separate from imported canonical data.          | Discord bridge previews do not mutate Echo canonical state until import commit.                                                  |
| 22  | Voice roster truth belongs to voice services.                              | UI does not merge participant identities, mute/deafen, or track state as canonical truth.                                        |
| 23  | Notification attention rules are centralized.                              | Mention, ping, and badge priority are computed outside components.                                                               |
| 24  | Search result authority belongs to server/backend/domain contracts.        | Client search UI does not broaden access or infer hidden results.                                                                |
| 25  | Upload validity is server-owned.                                           | Client preflight mirrors UX constraints but server presign and validation remain authoritative.                                  |
| 26  | Settings persistence owns conflict handling.                               | Settings views do not merge stale editor state with fresh domain state without a service authority.                              |
| 27  | Server rules remain on the server/domain side.                             | Client code can preview or explain rules but cannot define enforcement behavior.                                                 |
| 28  | Audit-log meaning is backend-defined.                                      | UI renders audit entries without reclassifying event semantics.                                                                  |
| 29  | Profile identity is normalized once.                                       | Components do not reconcile user, member, and social profile identity independently.                                             |
| 30  | Friend and block rules live in the social domain.                          | UI does not infer relationship state from presence, DM threads, or cached users.                                                 |
| 31  | Guest/account upgrade rules remain in account identity.                    | Shell code does not decide session trust, upgrade eligibility, or binding validity.                                              |
| 32  | OAuth and passkey flows stay account-owned.                                | Components render flow state and submit intents only.                                                                            |
| 33  | Rate-limit and abuse semantics are backend-owned.                          | Client throttling is UX only and not relied on for policy.                                                                       |
| 34  | Error code meaning comes from contracts.                                   | UI maps documented codes to messages without inventing new states.                                                               |
| 35  | Feature flags and production gates are not inferred by views.              | Views consume explicit config/domain capabilities.                                                                               |
| 36  | Theme and layout preferences stay presentation-owned.                      | Theme code does not decide product/domain truth.                                                                                 |
| 37  | Accessibility state is presentation-owned.                                 | ARIA, focus, and keyboard behavior do not carry domain policy.                                                                   |
| 38  | Local draft state remains local.                                           | Drafts do not alter canonical message, upload, or thread state before submit.                                                    |
| 39  | Pinned/reaction/read-state contracts remain server-backed.                 | Client displays current contract state and sends intents.                                                                        |
| 40  | Channel visibility is policy-derived.                                      | Client filtering consumes policy outputs, not reconstructed permission rules.                                                    |
| 41  | Member list sorting is presentation unless it encodes hierarchy.           | Hierarchy-aware ordering comes from roles/permissions services.                                                                  |
| 42  | Server onboarding flow does not invent membership truth.                   | Onboarding code consumes explicit membership and invite outcomes.                                                                |
| 43  | Invite validity is backend-owned.                                          | Client never treats local parsing as authorization.                                                                              |
| 44  | Metrics and diagnostics are observational only.                            | Diagnostics do not mutate or select canonical domain state.                                                                      |
| 45  | Storage mode decisions are server/backend/config-owned.                    | Client code does not infer mock, memory, or Postgres semantics beyond documented config.                                         |
| 46  | E2EE safety state has one cryptographic authority.                         | UI renders verified device/session state without deciding cryptographic trust independently.                                     |
| 47  | Voice E2EE preparation remains transport/security-owned.                   | Voice UI does not define key readiness or fallback security policy.                                                              |
| 48  | Public ids and ordering use documented snowflake semantics.                | Client code does not mix wall-clock ordering into canonical timelines.                                                           |
| 49  | Domain migrations have explicit owners.                                    | Temporary compatibility code is tracked and retired after migration.                                                             |
| 50  | Cross-domain adapters are thin.                                            | Adapters translate between stable APIs without merging truth from both sides.                                                    |
| 51  | View models may shape display state only.                                  | View models do not become hidden canonical stores for backend state.                                                             |
| 52  | Charter exceptions are documented where they remain.                       | Known tensions link back to this checklist and the violation inventory.                                                          |
| 53  | Inventory completeness is maintained with file moves.                      | New stores, feature roots, API modules, and route files update the domain map and charter inventories.                           |
| 54  | Simulations are clearly labeled and cannot be confused with live policy.   | Role previews or demo behaviors are marked as simulations and never enforce real permissions.                                    |
